# OpenAPI document and a typed client (E5.4)

E5.4 was deferred until a second consumer of the REST surface appeared. The E11 app (Expo, for the web and phones; #37–#43) is that consumer. It needs the routes described in a standard form, typed responses it can trust, and one correct implementation of the token refresh that the reference page (E5.3) found easy to get wrong. This story adds both, generated from the Zod schemas the routes already validate with. Built offline: no SchoolSoft login, no BankID round and no request to schoolsoft.se took place.

This branch builds on E5.6 (the overview and the schedule's dates): the overview is the app's first call, and a document generated without it would drift the moment E5.6 merged.

<frozen-after-approval>

## Intent

`docs/reference/openapi.json` is an OpenAPI 3.1 document of `/api/v1`, generated by `make docs` from the route table, the operations' input and output schemas, the overview schema, the session schema and the problem schema. CI refuses it when it is stale. `schoolsoft-agent/client` is a small typed client for the E11 app and anyone else. It calls every route, validates every answer against the same schemas, owns the token refresh with single-flight, and turns every failure into one error type carrying the existing error kinds.

## Scope

In: the OpenAPI document and its drift check; a Zod schema for `/api/v1/session` and the connector's `/children` projection; the client (routes, validation, refresh, errors) as a subpath export; a boundary rule that keeps the client free of the connector's code; the REST reference, the connector guide, the stability policy and the architecture page.

Out: the OAuth sign-in itself (registration, PKCE, the redirect). It is platform-specific and belongs to E11.5; the client starts from tokens the app already holds. Also out: serving the document from the connector, CORS (E5.7), response metadata (E5.5), code generators for other languages (the document is standard, so any OpenAPI 3.1 tool can read it).

## The OpenAPI document

**Generated, not written.** `src/http/openapi.ts` builds the document from:

- `restRoutes()`: one path per route, with the path parameter `childId` and a query parameter per input field, each with the JSON Schema of its Zod field (so `week` is an integer 1–53, `fresh` a boolean);
- the overview's path and `OVERVIEW_QUERY`;
- the response schemas: each operation's `output`, the overview's `OverviewSchema`, a new `SessionSchema` and `ConnectorChildrenSchema` (`src/http/api-schemas.ts`), and `ProblemSchema`;
- `PROBLEMS`: one response per status a route can answer, `application/problem+json`, described by the problem types that use it.

`z.toJSONSchema` (Zod 4, already a dependency) produces JSON Schema 2020-12, which OpenAPI 3.1 uses as it is. No generator dependency is added. Each response schema is one component (`#/components/schemas/Schedule`, …). `additionalProperties: false` is removed everywhere. The stability policy says new response fields are compatible and consumers must ignore fields they do not know, so the document must not tell generators otherwise.

**Security.** One `oauth2` scheme with the authorization-code flow at the connector's `/authorize` and `/token`, and one scope per operation. A route requires its operation's scope. The overview lists its three scopes as alternatives, since any one of them is enough. `/session` needs a valid token and no scope.

**The resource is named after MCP.** The document and the client docs say it plainly. The connector is one OAuth protected resource, `https://<connector>/mcp`, whose metadata is at `/.well-known/oauth-protected-resource/mcp`. A REST client asks for tokens with `resource=https://<connector>/mcp`, and the `401` challenge on `/api/v1` points to that metadata. **No `/api/v1` alias** is added. RFC 9728 requires the `resource` in protected-resource metadata to equal the identifier its well-known URL was built from. Metadata at `/.well-known/oauth-protected-resource/api/v1` would therefore have to name a second resource, `<connector>/api/v1`. Tokens would then need a second audience, and the token check a second accepted value. That widens what a token is good for in exchange for a name. It is neither clean nor safe, so the name stays and is documented.

**Stays current.** The document is one more entry in `scripts/gen-docs.ts`'s `OUTPUTS`, so the existing generated-docs test (`test/boundary/generated-docs.test.ts`) and CI's "Generated docs and skills are current" step refuse a stale copy. That is the repository's pattern for generated references; no separate target is added. A test also walks the document against the router: every route the router serves is in the document with the same method, parameters and scopes, and nothing else is.

`info.version` is the API version (`1`), not the package version, so a release does not make the document stale.

## The typed client

**Where it lives: a subpath export of this package**, `schoolsoft-agent/client` (`src/client/`, built by `tsc` into `dist/client/`, `"./client"` in `exports`). Alternatives considered:

- *A separate workspace package*: its own version, release-please component, publish job, provenance and registry settings. That is a second release pipeline for about 300 lines, and the client must change in lockstep with the routes anyway. Its versions would only ever mirror this package's.
- *Generated into `dist` only*: nothing to review or test in the source tree, and no place for the refresh logic, which is hand-written.

A subpath needs one `exports` line that publint checks, ships with the release that changes the routes, and follows the same stability policy. The cost is that installing it also installs the package's own dependencies (Express, the MCP SDK, Commander, ssp-node), though a bundler never touches them. The client's runtime imports are `zod` and its own directory, nothing else; a boundary rule enforces it. Metro and Vite therefore bundle only the client and Zod. If the install footprint matters for E11, the same directory can be published as its own package later without changing its API.

**Generated from the same schemas.** `make docs` also writes `src/client/api.gen.ts`, checked in and drift-tested like the document. It holds:

- the response schemas as JSON Schema (the document's components);
- TypeScript types emitted from those schemas by a small emitter in `scripts/` (objects, arrays, unions, `const`, `enum`, nullability, with the descriptions as doc comments);
- the query parameter types per route and the list of problem names and error kinds.

At run time the client turns each JSON Schema back into a Zod validator with `z.fromJSONSchema`, once per schema. The chain Zod → JSON Schema → Zod is tested: every fixture the connector's own schema accepts, the client's validator accepts, and the drifts the connector refuses (a malformed date, an unknown `status`, a missing field, an unknown `kind`), the client refuses too. Unknown fields pass, as the policy requires.

**Calls.** `createClient({ baseUrl, clientId, tokens, fetch?, language?, now? })`, then:

| Method | Route |
| --- | --- |
| `session()` | `GET /api/v1/session` |
| `children()` | `GET /api/v1/children` |
| `schedule(childId, { week?, fresh? })` | `GET /api/v1/children/{childId}/schedule` |
| `calendar(childId, { start_date?, end_date?, fresh? })` | `…/calendar` |
| `lunchMenu(childId, { week?, fresh? })` | `…/lunch-menu` |
| `overview(childId, { date?, fresh? })` | `…/overview` |

Query names are the API's own; there is no renaming layer to drift. A test asserts that the methods and the document's operations are the same set.

**Tokens.** `tokens` is a `TokenStore` (`load`, `save`, `clear`; a memory store is provided). The app decides where tokens live (memory plus secure storage on phones, E11.5). The client loads them once, keeps the current pair in memory, and saves every rotation before it uses the new access token.

**Refresh, single-flight.** Access tokens live 5 minutes. Refresh tokens rotate, and presenting one twice revokes the whole grant (the connector's reuse detection). So:

1. At most one refresh request is in flight per client. Every caller that needs a fresh token while one is running awaits that same promise.
2. A request that got `401` with access token *A* refreshes only if *A* is still the current token. If another request already rotated it, it simply retries with the new one. This check is synchronous against the in-memory pair, so there is no window in which two callers both decide to refresh.
3. A token known to be expired (from `expires_in`, with 30 seconds of margin) is refreshed before the request rather than after a `401`.
4. Each request is retried at most once after a refresh. A `401` on the retry, or a refused refresh (`invalid_grant`: revoked, expired, reused), clears the store and fails with `oauth-token`: the app must connect again.
5. The refresh request is `grant_type=refresh_token` with `client_id` and `resource=<connector>/mcp`, as a public client.

**Errors.** Every failure is a `ConnectorError` carrying the kinds the MCP tools and the CLI already use: `kind`, `retryable`, `status`, `problem` (the problem type's name, e.g. `schoolsoft-session`), `detail`, `hint`, `ownerDashboard`, `retryAt`, and the full problem body when there was one.

| Condition | `kind` | `problem` | `retryable` |
| --- | --- | --- | --- |
| Any `application/problem+json` answer | the body's | the body's type | the body's |
| `401` that survives one refresh, or a refused refresh | `not_authenticated` | `oauth-token` | false |
| No tokens in the store | `not_authenticated` | `oauth-token` | false |
| `fetch` throws (offline, DNS, TLS) | `network` | none | true |
| A `2xx` whose body does not fit the schema | `upstream` | `response-drift` | false |
| Any other answer (a proxy's HTML error page) | `upstream` | none | `status >= 500` |

The client never retries on its own except the single retry after a refresh. `retryAt` and `Retry-After` are for the app to honour, since the connector's budget and breaker exist to keep traffic down.

## I/O and edge cases

| Input or condition | Required behaviour |
| --- | --- |
| A route added to the table without regenerating | The generated-docs test fails |
| The document vs the router | Same paths, methods, parameters and scopes; the test fails otherwise |
| Five parallel calls, all `401` | Exactly one refresh request; all five retried once with the new token |
| A `401` after another call already rotated the token | No refresh; retried with the current token |
| Refresh answers `400 invalid_grant` | Store cleared; every waiting call fails with `oauth-token`; no second refresh |
| Access token past `expires_in` | Refreshed before sending; no `401` round trip |
| `409 schoolsoft-session` | `ConnectorError` with `ownerDashboard`, no refresh |
| `503 portal-pushback` | `ConnectorError` with `retryAt`, no retry |
| A schedule without `startDate`, an overview section with `status: "weird"` | `response-drift` |
| A response with a field the client does not know | Accepted, passed through |
| The client importing anything but `zod` and its own files | `make boundaries` fails |

## Code Map

- `src/http/api-schemas.ts`: `SessionSchema`, `ConnectorChildrenSchema`; `rest.ts` validates the session answer with it.
- `src/http/openapi.ts`: the document.
- `src/client/index.ts`: the client; `src/client/api.gen.ts`: generated schemas and types.
- `scripts/gen-docs.ts`: `docs/reference/openapi.json`, `src/client/api.gen.ts`; `scripts/json-schema-ts.ts`: the type emitter.
- `scripts/check-boundaries.ts`: the client's import rule and its exemption from the portal-outbound rule (it talks to the connector, never the school portal).
- `package.json`: `"./client"` export; `scripts/pack-smoke.sh`: imports it from the installed tarball.
- Tests: `test/unit/openapi.test.ts`, `test/unit/client.test.ts`, `test/functional/http-client.test.ts` (the client against the real connector), `test/boundary`.
